# Implementation Plan: Session Actuals at Feedback Time

**Branch**: `feat/session-actuals` | **Date**: 2026-10-23 | **Spec**:
[spec.md](spec.md)

## Summary

The feedback record gains a per-activity record of what the user
actually performed: repetitions or duration, load, an optional
display name, and a not-performed flag. The record lives on the
existing per-user feedback row, keyed by activity ID. The
prescription on the training never changes. The generation
pipeline reads the performed values, in place of the prescribed
ones, when it folds recent sessions into progression signals and
into the history prompt.

## Technical Context

**Language/Version**: Go (backend), Dart/Flutter (app)

**Primary Dependencies**: gorm with AutoMigrate for the schema,
fiber for the HTTP layer, the repository codegen for the Dart models

**Storage**: one additive `jsonb` column on the feedback table

**Testing**: Go unit tests beside the code (service, llm, model);
Flutter widget tests in the app test tree

**Target Platform**: production backend on merge; Android app

**Project Type**: mobile + API

**Constraints**: the prescription of a completed training is a
historical record and stays immutable; the feedback write stays
backward compatible for app versions that send no actuals

## Constitution Check

- Production Care: the change ships additive schema only. The
  deploy verification reads the live feedback of a real training
  after the rollout.
- Data Compatibility: one additive column, no rewrite of existing
  rows. Old rows read as no actuals recorded.
- Generation Integrity: the consumption change lands with unit
  tests on the signal folding. The integration trajectory harness
  needs a live model provider and cannot run in the automation
  environment; the pull request declares the gap.
- Tests and the Coverage Gate: new code carries tests beside the
  code it covers; the 90% unit coverage gate stands.
- Minimal Owned Surface: no new dependency. The actuals type is
  product logic and stays in the model package.

**Structure Decision**: the actuals record hangs on the feedback
row because the feedback step is its single entry point and the
row already carries the (training, user) uniqueness. Keying by
activity ID keeps two instances of one exercise distinct and gives
the rename a per-instance home.

## Complexity Tracking

No constitution violation to justify. The one design point worth
recording: the generation fold applies actuals to in-memory copies
of recent trainings, never to stored rows, so the history prompt
and the signal folding share one performed view and the stored
prescription stays untouched.
